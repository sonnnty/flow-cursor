# สถาปัตยกรรม

## การข้ามจอ

เมื่อเมาส์ชนขอบจอที่ผังบอกว่าต่อกับอีกเครื่อง agent ของเครื่องนั้นจะจับเมาส์และคีย์บอร์ดของตัวเองไว้ แล้วส่ง event ให้เครื่องปลายทางจำลองต่อ
เลื่อนต่อไปเครื่องที่สามได้ เลื่อนกลับก็คืนการควบคุมให้เครื่องตัวเอง

ตำแหน่งที่เมาส์เข้าเครื่องปลายทางคิดตามสัดส่วน ชนขอบที่ครึ่งความสูงจอ ก็เข้าที่ครึ่งความสูงของอีกจอ แม้ความละเอียดต่างกัน

## P2P และ relay

hub เป็นคนจัดการ ส่วน input ไม่ผ่าน hub ถ้าไม่จำเป็น

- **hub** เก็บรายชื่อเครื่อง ผังจอ การตั้งค่า ว่าใครคุมใคร และที่อยู่ของแต่ละเครื่อง ส่งต่อคลิปบอร์ด และแจกไฟล์อัปเดต
- **input** วิ่งตรงจาก agent ถึง agent (P2P) ถ้าเส้นตรงใช้ไม่ได้ จะส่งผ่าน hub แทน (relay)
  แล้วเช็คเส้นตรงเป็นระยะ ได้ pong ติดกันสองครั้งก็กลับไปใช้ P2P

ระหว่างสลับเส้นทาง ปุ่มไม่หายและไม่ซ้ำ ทุก event มีเลขลำดับ ฝั่งส่งเก็บไว้จนได้ ack และส่งซ้ำตอนเปลี่ยนเส้นทาง
ฝั่งรับทำแต่ละเลขครั้งเดียวตามลำดับ หลังสลับ ฝั่งส่งบอกชุดปุ่มที่กดค้างอยู่ ฝั่งรับปล่อยปุ่มที่ไม่ตรงกัน

การขยับเมาส์ส่งเป็น QUIC datagram พร้อมตำแหน่งจริง datagram ที่หายไปจึงไม่มีผล

ถ้า hub ล่ม เครื่องที่เคยต่อกันแล้วยังคุมกันผ่าน P2P ได้ แต่ relay ใช้ไม่ได้

## ความปลอดภัย

ทุกอย่างวิ่งบน QUIC (`quinn`, TLS 1.3) ข้อมูลคีย์บอร์ดไม่เคยวิ่งแบบไม่เข้ารหัส

- hub มีตัวตนถาวร (certificate ที่เก็บใน volume)
- agent แต่ละเครื่องสร้าง key และ certificate ของตัวเอง private key ไม่ออกจากเครื่อง fingerprint ของ certificate คือตัวตนของเครื่อง
- join token มีรูปแบบ `FC1-<secret>-<ส่วนต้นของ fingerprint ของ hub>`
  agent จึงยืนยันตัวตน hub ได้ก่อนส่ง secret แล้วจำ fingerprint เต็มของ hub ไว้ใช้ตลอด
- hub เทียบ token แบบใช้เวลาคงที่ และหน่วง 500 ms เมื่อ token ผิด
- P2P ยืนยันตัวตนทั้งสองฝั่ง ฝั่งรับยอมเฉพาะ fingerprint ที่ hub แจกมา ยกเลิกสิทธิ์เครื่องใน dashboard แล้วทุกเครื่องตัดการเชื่อมต่อกับเครื่องนั้นทันที
- เครื่องหนึ่งปลอมเป็นอีกเครื่องไม่ได้ เพราะฝั่งรับใช้ตัวตนจากการเชื่อมต่อ ไม่ใช่จากข้อความ
- แบบ relay เข้ารหัสทีละช่วง hub จึงเห็น event ใน process ของตัวเอง

## Keycode

ทุกเครื่องใช้ USB HID usage code เป็นรหัสกลาง แล้วแปลงเป็น evdev `KEY_*` บน Linux และ scancode บน Windows
ไม่ใช้ VK code จึงไม่ขึ้นกับ keyboard layout ของแต่ละเครื่อง

## Agent และ tray

agent เป็น process ที่ไม่มี UI รันอยู่ตลอด `flow-tray` เป็นโปรแกรมแยกที่คุยกับ agent ผ่าน local IPC
ไม่มี tray ก็ใช้งานได้ เช่นเครื่องที่ไม่มีจอ: `flow-agent run`

ข้อความ IPC เป็น JSON บรรทัดละข้อความ มีเลขเวอร์ชันทุกข้อความ
socket และ named pipe เปิดให้เฉพาะผู้ใช้คนนั้น Linux ตรวจ uid ของผู้เชื่อมต่อทุกครั้ง

หน้าต่างสถานะใช้ egui กับ OpenGL ไอคอนบน Linux ใช้ `ksni` (D-Bus ไม่ต้องมี GTK) บน Windows ใช้ `tray-icon`

## โครงสร้าง repo

Cargo workspace เดียว เขียนด้วย Rust ทั้งหมด

| โฟลเดอร์ | หน้าที่ |
| :--- | :--- |
| `proto/` | ข้อความทั้งหมด (`postcard`) |
| `crates/keymap` | ตารางแปลง HID, evdev, scancode และชื่อปุ่ม |
| `crates/layout` | ผังจอและการคำนวณข้ามขอบ |
| `crates/net` | ตัวตน, QUIC, join token, mDNS, การสลับ P2P กับ relay |
| `crates/ipc` | โปรโตคอล local IPC ระหว่าง agent กับ tray |
| `crates/version` | เวอร์ชันและ build id |
| `crates/itest` | integration test |
| `server/` | `flow-server` และ dashboard ที่ฝังอยู่ใน binary |
| `agent/` | `flow-agent` และ backend `wayland`, `x11`, `windows`, `sim` |
| `tray/` | `flow-tray` |
| `tools/bench` | `flow-bench` วัด latency |
| `build/`, `deploy/` | สคริปต์ build, Dockerfile, compose, ตัวติดตั้ง, systemd unit, ไอคอน |
